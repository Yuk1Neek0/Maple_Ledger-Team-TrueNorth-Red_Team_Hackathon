The business process

Four blocks. One scored core.

End-to-end, the system is a four-stage pipeline: a supplier issues a signed record, the backend links & stores it into a chain, verifies a product on request, and the buyer sees the result. Only the Verify block is harness-scored.

05
Inside the scored core

Verification in three layers.

The Verify block decomposes into three layers, applied in order. Two of them can change the verdict; the third only advises. This is the line the whole architecture defends: crypto & arithmetic decide, AI only flags.

L1Deterministic gates
Integrity · structural · quantity
Schema + signature + registry (M2.1 / P0), broken-link / cycle / replay (M3.1 / P1), mass-balance (M3.2 / P1). Fixed precedence; a failed node is excluded or the chain rejected. Changes the verdict.
L2The math
Cost by country → thresholds → verdict
Sum integer cents, apply 98 / 51, require last substantial transformation in Canada (M2.3 / P0). Pure arithmetic. Produces the verdict.
L3Plausibility · advisory
Anomaly / risk score
A real signature with implausible numbers (M3.3 / P1). Queues a record for an auditor. Never changes the verdict.
▸Maps to DESIGN §7 (pipeline) and §9 (anomaly taxonomy). The five primer test categories live in L1; the #1 scored deliverable is L2. Only L1 and L2 touch the verdict — L3, and any AI, is advisory by rule.
06
The data structure

Two layers: a signed fact, and a verifier's view.

Each supplier contribution is one immutable, signed Attestation. The verifier never edits it — it wraps each in a mutable Node for everything it computes. Annotating the signed object would change its hash and break the chain.

Attestation — immutable, signed
  • supplier_id — maps to a registry key
  • output (product_id, quantity, unit)
  • inputs[] — hashes of consumed records
  • materials_cents / labour_cents — integer cents
  • work_country · is_substantial_transformation
  • signatures[] — Ed25519
  • id = hash(canonicalize(payload))
Node — mutable, verifier's view
  • input_hashes / consumer_hashes — bidirectional edges
  • sig_valid · signer_known · status (OK / INVALID)
  • cost_by_country · subtree_cents — memoized
  • annotations — overlay (P3), never signed
  • anomalies[]
▸Stored as a map<hash, Node> — a content-addressed DAG, not a tree. Money is integer cents, never floats. This is the canonical model in build-execution-plan-en.md §3.1; DESIGN §4 is the diagram view of the same thing.

08
When a node breaks

Contained — but a tampered product can't be certified.

Two scopes of "broken." A tampered or unverifiable node means the product that depends on it can't be certified (UNVERIFIABLE) — you never silently drop it and recompute, because dropping a foreign node would inflate the %. But the damage is scoped: upstream, other products, and the system never collapse, and the run never crashes.

UPSTREAMUntouchedself-validates; doesn't depend on anyone downstream.
TAMPERED NODECost untrustedcan't trust its number — can't include it or drop it.
ITS PRODUCTUNVERIFIABLEa chain with a forged link can't be honestly certified.
OTHERS & SYSTEMUnaffectedother products still certify; no crash.
UNVERIFIABLEcan't certify
SIGNATURE_INVALID · UNKNOWN_ISSUER · BROKEN_LINK · MALFORMED (required field)
Cost base can't be trusted → no honest %. Never dropped from the sum — dropping a foreign node would inflate the Canadian %. Upstream & other products untouched.
NONErejected
MASS_BALANCE (over-claim / fraud) · CYCLE (can't be traversed)
The chain is provably wrong or untraversable → the product is rejected outright.
CERTIFIESadvisory
Anomaly risk score (M3.3) · missing optional field
A real signature with implausible numbers is flagged for review, verdict unchanged; a missing optional field degrades gracefully. The only "still certifies" cases.
▸Why UNVERIFIABLE, not a "degraded number"? A provenance system that silently works around a forged link is worthless — and dropping an unverifiable foreign node would inflate the %. Why it doesn't cascade: each node self-validates and inputs are hashes, not pointers, so other nodes stay valid and nothing crashes. Aligned with DESIGN §7 and build-execution-plan §3.3.

10
P0 · the legal output

The math, exactly. No AI, ever.

Business questionWhat percentage is Canadian, and which label applies? The #1 scored deliverable and the part a court could audit — pure, reproducible arithmetic in integer cents, never floats.
totalCostCents = Σ contribution.totalCostCents over the chain
canadianCostCents = Σ contribution.canadianCostCents over the chain
percent = round( canadianCostCents / totalCostCents × 100 )
≥ 98% & last ST in CAPRODUCT_OF_CANADA98% threshold, verbatim from the Competition Bureau.
≥ 51% & last ST in CAMADE_IN_CANADA51% threshold, verbatim.
otherwiseNONEBelow 51%, or last substantial transformation not in Canada.
▸Both conditions are required — cost threshold and last substantial transformation in Canada (Competition Bureau). The primer says the spec defines how to identify "substantial transformation." Our Phase-0 assumption is a guess — confirm it on 5.30 morning before trusting the verdict.
11
P1 · catch the forger · the deterministic half

Five test categories → named rejections.

Business questionWhat happens when the data is manipulated or incomplete? The primer's five categories are graded directly. Each maps to a deterministic check with a named reason code — the right reason for the right failure.
01
SIGNATURE_INVALID
Integrity: record altered after signing — fingerprint no longer matches.
02
UNKNOWN_ISSUER
Integrity: signer not in the verified registry, or that key doesn't verify the signature.
03
REPLAY_DETECTED
Replay: attestation reused across chains / duplicate output serial.
04
BROKEN_LINK / CYCLE
Structural: dangling input reference, impossible ordering, self-reference.
05
MASS_BALANCE
Quantity: more material consumed than upstream ever produced.
06
MALFORMED
Incomplete: missing required fields — flag and degrade, don't crash.
Fixed precedence (a record fails on the first applicable code):  MALFORMED → SIGNATURE_INVALID → UNKNOWN_ISSUER → REPLAY_DETECTED → BROKEN_LINK / CYCLE

P1 · catch the forger · the plausibility half

The signature is real. The numbers lie.

Crypto for integrity — deterministic
  • Edited record → signature fails
  • Fake supplier → not in registry
  • Mass-balance closes the over-claim attack across the graph
  • But a real supplier signing inflated-but-valid numbers passes every crypto check
AI for plausibility — advisory only
  • Labour cost 5× the regional norm → risk 0.94
  • Throughput above attested capacity
  • Geographic / temporal implausibility
  • Queues the record for an auditor — never alters the verdict

16
Before 5.30 · the plug-in boundary

Six adapters absorb the event-day spec.

The full schema, serialization rules and registry arrive at kickoff. Everything uncertain hides behind these six signatures. We freeze the signatures now; on 5.30 we rewrite only the insides. The core, graph, math and UI consume adapter outputs — they don't change.

validate(obj) → ResultSwap the schema file.
canonicalize(obj) → bytesDSSE / JCS / custom — the signing input.
verify(bytes, sig, key) → boolCall the reference library.
resolveKey(keyid) → publicKeyRead the registry shape.
getCosts(att) → CostBreakdownMap cost fields → integer cents.
findLastST(chain) → AttestationWhatever the spec's substantial-transformation rule turns out to be.
▸If the boundary is right, 5.30 morning is 1–2 hours of mechanical translation, not design. The event is a single day, so all the design pressure lands on the prep window before it.
