02
Why this order

The harness decides the priority. Not us.

The automated scoring harness grades exactly three things. Everything we build is ranked by how directly it moves one of these scores. The supplier and purchaser UIs are required and carry the demo, but the harness does not score them — so they sit below the scored core.

#1
Canadian content computation — is the percentage and verdict correct?
#2
Anomaly detection — are manipulated chains caught and classified?
#3
Edge-case handling — does it stay standing on incomplete / adversarial data?
Two filters applied to every line of the design: (1) is it in the primer's scope? (2) if it's out of scope — is it cheap to build and strong on stage? If a feature is both hard to build and invisible in a demo, it's cut.

04
P0 · the scored core

The verification backend — the spine.

Business question Can a buyer trust this product is Canadian — without trusting the supplier, and reproducibly by anyone? An HTTP service ingests the attestation chain, proves nothing was altered, and computes the legal verdict.
Adopt use a vetted library/standard Build deterministic code we write AI advisory, never in the verdict path
Adoptpyca/cryptography — Ed25519 verify AdoptSHA-256 — content addressing of each attestation AdoptDSSE — signing envelope (from the event-day reference library) AdoptJSON Schema 2020-12 — reject MALFORMED records AdoptULID — attestation IDs Adoptin-toto — the attestation pattern we cite in the pitch BuildverifyAttestation() — signature + schema gate BuildwalkChain() — traverse the DAG of inputs
Don't reimplement crypto. Event day ships a reference library for signing/verifying — call it. Canonical serialization (DSSE vs. JCS) is decided by that library, not by us. Our job is to wire it, not rebuild it.
05
P0 · the legal output

The math, exactly. No AI, ever.

Business question What percentage is Canadian, and which label applies? This is the #1 scored deliverable and the part a court could audit — so it is pure, reproducible arithmetic.
totalCostCents  =  Σ contribution.totalCostCents   over the chain
canadianCostCents  =  Σ contribution.canadianCostCents   over the chain
percent = round( canadianCostCents / totalCostCents × 100 )
otherwiseNONEBelow 51%, or last substantial transformation not in Canada.
≥ 51% & last ST in CAMADE_IN_CANADAThe 51% legal threshold, verbatim from the Competition Bureau.
≥ 98% & last ST in CAPRODUCT_OF_CANADAThe 98% legal threshold, verbatim.
AdoptCompetition Bureau thresholds — 98 / 51, hard-coded constants BuildcomputeCanadianContent() Buildinteger cents — no floats (float math diverges across runtimes)
The primer says the event-day spec defines how to identify "substantial transformation." Our current assumption (a flag on tier-0) is a guess — confirm it against the spec on 5.30 morning before trusting the verdict.
06
P1 · catch the forger · the deterministic half

Five test categories → named rejections.

Business question What happens when the data is manipulated or incomplete? The primer's five test categories are graded directly. Each maps to a deterministic check with a named reason code.
01
SIGNATURE_INVALID
Integrity: record altered after signing — fingerprint no longer matches.
02
UNKNOWN_ISSUER
Integrity: signer not in the verified registry, or key doesn't verify.
03
REPLAY_DETECTED
Replay: wrong product, duplicate ID / nonce — chain reuse.
04
BROKEN_LINK / CYCLE
Structural: dangling input, bad ordering, self-reference.
05
MASS_BALANCE
Quantity: more material consumed than upstream ever produced.
06
MALFORMED
Incomplete: missing required fields — handle uncertainty, don't crash.
Fixed precedence (a record fails on the first applicable code):   MALFORMED → SIGNATURE_INVALID → UNKNOWN_ISSUER → REPLAY_DETECTED → BROKEN_LINK / CYCLE
07
P1 · catch the forger · the plausibility half

The signature is real. The numbers lie.

Crypto for integrity — deterministic

Catches tampering

  • Edited record → signature fails
  • Fake supplier → not in registry
  • But: a real supplier signing inflated-but-valid numbers passes every cryptographic check
AI for plausibility — advisory

Catches lying

  • Labour cost 5× the regional norm → risk score 0.94
  • Throughput above attested facility capacity
  • Geographic / temporal implausibility
  • Queues the record for an auditor — never alters the verdict
AIscikit-learn IsolationForest / PyOD — unsupervised anomaly score AIXGBoost / LightGBM — supervised cost-outlier (if labels exist) AdoptStatsCan wage data + NAICS — the benchmark features
This is the second scored dimension and the cleanest 30 seconds on stage: a valid signature, a 0.94 risk score, the auditor queue lighting up. Crypto for integrity, AI for plausibility — demonstrated live.
08
P1 · the provenance graph

Flat attestations → a chain of custody.

Business question Where did every dollar come from, and is the structure sound? Each attestation references the fingerprints of the ones it consumed. That forms a DAG we traverse for the math and render for the buyer.
Buildcontent-addressed references — SHA-256 links, no bespoke hash-chain BuildbuildGraph() — nodes + edges from the inputs array Buildvisited-set cycle guard Buildmass-balance check — closes the over-claim attack AdoptCytoscape.js / React Flow / D3 — render any DAG
Render against the Graph shape, never a library-specific format — event-day data could be a 4-node toy or a 50-node tree. Node colour is driven by the reason-code status, so a broken link is visible at a glance. The graph is both a scored structure and a demo centrepiece.

P3 · bonus · only after P0–P2 ship

AI flair — the bonus, not the wage.

Highest ROI · ~½ day Natural-language verifier

"Which components trace back to one foreign sub-supplier?" → Claude rewrites it into a deterministic graph query → answer cites attestation IDs. Numbers come from the math, never the model.

Demo gold · ~½ day Conversational authoring

Supplier types "we milled 50 airframes, 3 machinists × 6 hrs at $42/hr" → LLM drafts the structured attestation → human signs. AI as accelerator, not authority.

Cleanest 30 sec Live anomaly on a cost-inflation attack

Already built in P1 — just script it into the demo. Valid signature, 0.94 risk score, auditor queue lights up.

Pitch story · ~10 min Reconciliation report (single canned example)

One hard-coded "CBSA import" example + an LLM-drafted comparison report. Strong defence-procurement story; the harness gives you nothing to reconcile against, so don't build the real pipeline.

Hard rule: if the core backend hasn't passed the happy path + all five test categories, don't touch a single P3 item. The bonus is the bonus. Earn the wage first.

12
5.30 readiness · the plug-in boundary

Six adapters absorb the event-day spec.

The full schema, serialization rules and registry arrive at 9 AM on event day. Everything uncertain hides behind these six function signatures. We freeze the signatures now; on 5.30 we rewrite only the insides.

validate(obj) → ResultSwap the schema file.
canonicalize(obj) → bytesDSSE / JCS / custom — signing input.
verify(bytes, sig, key) → boolCall the reference library.
resolveKey(keyid) → publicKeyRead the registry shape.
getCosts(att) → CostBreakdownMap the cost fields → integer cents.
findLastST(chain) → AttestationWhatever the spec's ST rule turns out to be.
If the boundary is right, 5.30 morning is 1–2 hours of mechanical translation, not design. The core, the graph, the math and the UI all consume adapter outputs — they don't change. The event is a single day, so all the design pressure is on the prep window before 5.30.
The one rule
Build what's scored. Polish what's demoed. Cut what's neither.
P0 and P1 win the harness. P2 carries the room. P3 is the encore — and only if the first three are done. Everything in the cut pile stays in the pitch as production roadmap and out of the single-day build.
